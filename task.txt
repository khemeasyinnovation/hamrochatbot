7. TARGET — RAG, Messages, Memory & Learners
RAG, history, memory and generation are complementary. They should not all be dumped into every prompt.
Context Meaning Use
Recent messages Short-term continuity Small window.
Conversation summary Compressed old history Replace long transcript.
Memory Durable useful facts Retrieve only when relevant.
KB/RAG Org/project facts Vector search + relevance threshold + small top-k.
Future PDFs/docs More Knowledge Chunk/index through existing Knowledge architecture.
Future live/news Fresh sources Separate ingestion/refresh design later.
Context budget
system/rules + user message + recent messages + relevant memory + top KB chunks
More stored knowledge must not mean larger prompts. The context builder selects the minimum useful information.
Memory rules
• Do not save every sentence as memory.
• Store useful preferences, facts, decisions and recurring context.
• Retrieve memory only when relevant.
• Long-term learning can grow retrieval/memory stores without retraining a model every time content changes.
Future Chat learners
The Chat workspace may eventually manage conversation learning, PDF/document learning and live-information learning.
“Learning” should be treated as a context/knowledge capability unless a separate real model-training project is approved.

19. DEFINITION OF DONE & HANDOFF
Area Done means
AI core Chat and Widget share a clear HamRobot response capability/provider boundary.
RAG Relevant chunks retrieved selectively; irrelevant context excluded.
Memory Only relevant durable memory is retrieved when implemented.
Context Bounded budget + recent-history strategy.
Widget fallback KB miss can route to HamRobot capability instead of repeated fallback.
Payment Unpaid public Widget cannot operate.
Usage Actual provider requests recorded server-side.
Allowance Managed AI stops clearly at zero; recovery shown.

Security No cross-org leakage; no raw API keys exposed/logged.
Regression Chat, KB, Widget, domains, payment and dogfooding remain working.
Handoff questions
• Is this CURRENT, TARGET, MIGRATION or FUTURE?
• Does the existing schema already have a home for it?
• Can it be a module rather than a new table/microservice?
• Does it preserve Chat vs Widget separation and the right-side in-app Widget?
• Does it minimize unnecessary model/token usage?
• Does it preserve tenant, domain, payment and credential security?
• What regression test proves it is safe?
• If it conflicts with this document, reconcile before coding.
Final system definition
HamRobot is one authenticated SaaS application with two primary product surfaces: Chat (owner AI workspace) and
Widget (paid website-assistant SaaS). The app also runs its own right-side Widget for support/demo/dogfooding. The
long-term AI path is HamRobot AI: deterministic logic + RAG + conversation context + selective memory + model
generation when needed. Gemini is the current managed engine, not the product identity. BYOK is optional. The migration
is additive and ordered. PDF/web Knowledge, learners, own/cooked models, Workflows, teams and advanced monitoring
remain explicitly deferred.
